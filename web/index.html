Off-site replica

Everything the server stores is continuously copied to a second machine, so this is not the only place the backups sit. An interrupted link shows up as a queue that catches up on its own once it is fixed — never as a failed backup.

Config backup

A single zip with the instances, users and runners. Instance passwords sit in it exactly as they are in the database — that is, encrypted, if [secrets] master_key is set. The keys are not in the archive; they belong with pki/ and are backed up separately (see docs/production.md). The archive does contain operator password verifiers, though — treat it as a sensitive file.

runs, logs and backup data are not in the archive

Config restore

The import replaces the whole configuration with the contents of the archive: whatever is not in it will not be here after the import. What will change is shown first, and only then do you confirm. Backup data, runs and logs are not deleted.

Wipe the server

Deletes all backups, dumps and logs as well as the entire run history. The keys, users, instances and approved runners stay — the server is immediately operational again, just without anything collected. This is the only action in Arcatum that deletes backups, and it cannot be undone.
